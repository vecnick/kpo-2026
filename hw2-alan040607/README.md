# ПОС — преподавательская оценка студентов

Учебный проект на Python для КПО, ДЗ №2: консольный модуль оценивания одного
курса с DDD, Ports and Adapters, тремя паттернами GoF и DI-контейнером.
Python 3.11+, только стандартная библиотека. Установка сторонних пакетов не нужна.

## Быстрый запуск

Откройте терминал в корне проекта:

```powershell
python -m pos
```

Команды проверки и демонстрации также выполняются из корня проекта:

```powershell
python -m unittest discover -s tests -v
python -m examples.demo
python -m pos --help
```

В PyCharm выберите интерпретатор Python 3.11+, тип запуска `Module name`,
модуль `pos` и корень проекта в качестве `Working directory`.

Демонстрация каждый раз создаёт отдельную папку `output/demo-*` с JSON и CSV,
запускает каждую команду новым процессом и проверяет ключевые результаты.
Рабочее хранилище пользователя не затрагивается.

## Возможности

- Добавление и просмотр студентов и критериев.
- Пошаговая сборка рубрикатора через пункт 12 меню, с сохранением целиком.
- Выставление, просмотр, исправление и отмена оценок.
- Итог студента и общая ведомость, две политики пропусков.
- Сохранение JSON между запусками, экспорт CSV с кириллицей.
- Понятные сообщения об ошибках; командный режим возвращает код 1 при ожидаемой
  ошибке, argparse — код 2 при неверной команде, успешная операция — код 0.

В меню можно увидеть идентификаторы и затем использовать их для операций.
Идентификаторы задаёт пользователь: например, `s1`, `hw`, `exam`.
Дробные числа вводятся с точкой. Неправильный ввод не завершает интерактивный сеанс.
Ctrl+C или конец ввода завершают меню без traceback.

## Правила и формула

1. ID и названия непустые, без управляющих символов. ID уникальны в своём наборе.
2. Максимум и вес критерия строго положительны. Сумма весов не обязана быть 1.
3. Балл конечный, от 0 до максимума включительно. Оценка возможна только для
   существующих студента и критерия данного рубрикатора.
4. На пару «студент — критерий» существует одна текущая оценка. Повторное
   выставление отклоняется; изменение требует отдельной команды `revise`.
5. Исправление и отмена отсутствующей оценки запрещены. Неудачное исправление
   сохраняет прежнее значение.
6. Ввод чисел ограничен модулем 1 000 000 000 и шестью десятичными знаками.
   `NaN` и бесконечность запрещены. Вычисления используют Decimal, точность 50.
7. Итог не сохраняется в модели или JSON: он вычисляется из текущего состояния.
8. Пустой рубрикатор означает «Нет критериев», а не нулевой результат.

```text
Итог = 10 × Σ(вес × балл / максимум) / Σ(вес)
```

Пример: ДЗ 16/20 с весом 0.4, экзамен 9/10 с весом 0.6 → **8.60**.
После исправления экзамена на 10 → **9.20**.
После отмены экзамена при политике `zero` → **3.20**.

Политики:

| Параметр | Поведение при пропусках |
|---|---|
| `--policy zero` (по умолчанию) | Пропуски дают нулевой вклад; веса остаются в знаменателе |
| `--policy strict` | Итог не рассчитан до появления всех оценок |

Округление `ROUND_HALF_UP` до двух знаков производится только в выводе и CSV.
При отсутствии результата CSV содержит пустую ячейку и объяснение в `status`.
Ведомость также показывает число пропусков.

Эти решения конкретизируют недоопределённые части задания. История исправлений,
редактирование/удаление студентов и критериев, несколько курсов, апелляции,
универсальный импорт и авторизация в объём проекта не входят. ТЗ позволяет
не реализовывать изменение/удаление студентов и критериев как самоцель.

## Карта DDD

Ubiquitous Language: Student / студент, Criterion / критерий, Evaluation /
оценка, Gradebook / ведомость с рубрикатором, FinalScore / итог.

| Объект | Роль | Обоснование |
|---|---|---|
| `Student`, `Criterion` | Entity | Идентичность задаётся ID; одинаковые названия не означают один объект |
| `Score`, `Weight` | Value Object | Неизменяемые значения с собственными проверками; сравниваются по значению |
| `Evaluation` | Value Object | Текущее значение оценки; самостоятельной истории/ID нет, исправление заменяет значение |
| `Gradebook` | Корень агрегата | Охраняет связи студента, критерия и оценки и уникальность ID |
| `FinalScoreService` | Domain Service | Расчёт объединяет рубрикатор и оценки; не принадлежит одному студенту или критерию |
| `GradebookRepository` | Repository, порт | Абстракция загрузки и сохранения целого агрегата |

Граница агрегата — ведомость одного курса. Это позволяет синхронно проверять
все инварианты в одном месте. Для большого многопользовательского приложения
такой агрегат был бы слишком крупным; здесь он соответствует масштабу задания.

Модель не анемичная: методы `assign_evaluation`, `revise_evaluation`,
`revoke_evaluation`, `add_student`, `add_criteria` содержат бизнес-правила.
Внутренние словари закрыты по соглашению Python, публичные представления доступны
только для чтения, вложенные объекты неизменяемы (`frozen=True`). Это API-защита
от случайных изменений, а не попытка запретить рефлексию Python.

При восстановлении JSON используются те же конструкторы и методы агрегата.
Нельзя записать в JSON 21/20 и получить допустимое состояние приложения.
Entity адресуются и сравниваются по ID в пределах своего типа. Например, два
`Student` с одинаковым ID и разными именами обозначают одну сущность; `Student`
и `Criterion` с одинаковым ID не равны. Поля состояния исключены из сравнения
через `field(compare=False)`, поэтому автоматически создаваемый хеш также
зависит только от ID. Value Object сравниваются по значениям всех полей.
Тесты сохранения отдельно сравнивают все поля, чтобы равенство Entity по ID
не скрывало потерю данных.

Методы приложения имеют аннотации параметров и результатов. Числовые
конструкторы принимают `Decimal`, строку или целое число, а в модели хранят
`Decimal`. Коллекции агрегата возвращаются как `Mapping` только для чтения.
Динамический `Any` ограничен границей JSON и разрешением зависимостей в
DI-контейнере; бизнес-методы используют конкретные типы и порты.

## Архитектура: Ports and Adapters

```text
pos/
  domain/       модель, инварианты, Repository-порт, Builder, Domain Service, Strategy
  application/  Facade/use cases, ReportRow, порт экспорта, ошибка хранилища
  adapters/     CLI, JSON, CSV, маппинг сохранённого документа
  bootstrap.py  DI-контейнер и composition root
  __main__.py   точка входа
tests/          unit, integration, architecture и CLI end-to-end тесты
examples/       воспроизводимая демонстрация
```

Стрелки ниже обозначают зависимости исходного кода, а не поток данных:

```text
CLI ──────────────> Application ──────────────> Domain
JSON adapter ─────> Repository port (Domain)
CSV adapter ──────> Export port / ReportRow (Application)
bootstrap ────────> конкретные реализации и внутренние абстракции
```

Домен не знает о JSON, CSV, консоли, DI и путях файлов. Application не импортирует
адаптеры. Порты заданы через `typing.Protocol`; реализации соответствуют им
структурно, наследование от Protocol не требуется.

Путь команды «выставить оценку»:

```text
CLI → Facade → Repository.load → Gradebook.assign_evaluation → Repository.save
```

Facade не копирует доменные проверки. Он координирует работу и сохраняет модель
только после успешного выполнения операции. Для отчёта загружается единый снимок
ведомости, а не отдельное состояние для каждого студента.

## Три паттерна GoF

| Группа | Паттерн и место | Задача и реальное применение |
|---|---|---|
| Порождающие | Builder: `domain/rubric_builder.py` | Собирает рубрикатор по шагам; пункт 12 меню передаёт весь набор в `add_rubric`. Ошибка не оставляет половину критериев в хранилище |
| Структурные | Facade: `application/services.py` | Даёт UI простой интерфейс сценариев, скрывая координацию хранилища, модели, расчёта и экспорта |
| Поведенческие | Strategy: `domain/scoring.py` | Подменяет правило допустимости расчёта при пропусках; `zero` и `strict` выбираются при сборке приложения |

Builder возвращает неизменяемый снимок: дальнейшие вызовы Builder не изменяют
уже собранный результат. Агрегат дополнительно проверяет пересечения с текущим
рубрикатором до добавления всего набора. Builder не является единственной
точкой защиты инвариантов.

Facade — это сам прикладной сервис, отдельной дублирующей обёртки нет.
Strategy изменяет конкретное бизнес-правило, а общая формула не дублируется.
Repository и DI используются дополнительно, но не выдаются за GoF-паттерны.

## DI-контейнер

`Container` в `bootstrap.py` реализует регистрацию провайдеров, ленивое создание
singleton-объектов, разрешение зависимостей и обнаружение циклов/повторных
регистраций. Это небольшой контейнер без сторонней библиотеки, а не только
набор ручных вызовов конструкторов.

```text
PosApplicationService
  ├─ GradebookRepository → JsonGradebookRepository
  ├─ FinalScoreService → MissingPolicy → zero / strict
  └─ ReportExporter → CsvReportExporter
```

Контейнер используется на краю программы. Сервисы получают зависимости через
конструкторы и не вызывают `resolve()` — Service Locator внутри логики отсутствует.
В тестах можно напрямую внедрить in-memory repository и нужную стратегию.

## Хранение и экспорт

JSON содержит `version: 1`, студентов, критерии и оценки. Decimal сохраняется
строкой без промежуточного float. Неизвестная версия, неверная схема и нарушение
инвариантов отклоняются. Отсутствующий файл означает новый пустой курс;
повреждённый файл не означает пустой курс и не перезаписывается при следующей
операции.

Сохранение: временный файл в той же папке → flush/fsync → `os.replace`.
Сбой замены не портит предыдущую версию. Это не многопользовательская транзакционная
БД: одновременное редактирование одного JSON несколькими процессами не поддерживается.
Каждый сеанс следует запускать последовательно.

CSV: UTF-8 BOM, разделитель `;`, стандартное экранирование кавычек. Текст, похожий
на формулу таблицы, получает начальный апостроф. Экспорт поверх JSON-хранилища
запрещён. Экспорт в существующий CSV заменяет его содержимое только после
успешной записи временного файла. При ошибке записи или замены старый отчёт сохраняется.

## Командный интерфейс и ручная демонстрация

Глобальные параметры `--data` и `--policy` указываются **до** команды.
Без команды запускается меню. Следующий пример рассчитан на новый файл данных:

```powershell
python -m pos --data output/manual.json add-student s1 "Анна Иванова"
python -m pos --data output/manual.json add-student s2 "Иван Петров"
python -m pos --data output/manual.json add-criterion hw "ДЗ" 20 0.4
python -m pos --data output/manual.json add-criterion exam "Экзамен" 10 0.6
python -m pos --data output/manual.json grade s1 hw 21
# Ожидаемая ошибка: превышение максимума. Остальные команды продолжаем вручную.
python -m pos --data output/manual.json grade s1 hw 16
python -m pos --data output/manual.json grade s1 exam 9
python -m pos --data output/manual.json total s1
# 8.60
python -m pos --data output/manual.json revise s1 exam 10
python -m pos --data output/manual.json total s1
# 9.20
python -m pos --data output/manual.json revoke s1 exam
python -m pos --data output/manual.json --policy strict total s1
# Не все оценки выставлены
python -m pos --data output/manual.json report
python -m pos --data output/manual.json export output/manual.csv
```

Дополнительные команды: `students`, `criteria`, `scores s1`.
В `grade`/`revise` можно передать `--comment "текст"`.

## Проверка качества и соответствие критериям

```powershell
python -m unittest discover -s tests -v
python -m examples.demo
```

Тесты проверяют границы баллов, нечисловой ввод, неизвестные связи, дубликаты,
атомарность добавления рубрикатора, исправление и отмену, ручной расчёт 8.60,
обе политики, нормализацию весов, сохранение/восстановление, повреждённые данные,
сбой замены JSON, CSV и защиту хранилища от экспорта. Есть проверка направления
импортов домена и end-to-end сценарий CLI в отдельных процессах. Тесты не требуют
интернета и используют временные каталоги; пользовательские данные не изменяются.

| Критерий ТЗ | Подтверждение |
|---|---|
| Функциональность — 2.5 | Меню, командный режим, демонстрация, CLI-тест |
| DDD — 2 | Entity/VO, агрегат с инвариантами, Repository, Domain Service |
| Архитектура — 2 | Слои, порты, зависимости внутрь, отдельный composition root |
| GoF — 2.5 | Builder, Facade, Strategy в работающих сценариях |
| DI и README — 1 | Реальный контейнер с провайдерами, документация, тесты |

Оценка 10 не гарантируется кодом: согласно ТЗ для 8–10 нужна защита с объяснением
решения и доработкой по новому требованию. Без защиты максимум — 7.

## Роль ИИ

При выполнении проекта использовался ИИ-помощник ChatGPT. Работа велась поэтапно:
сначала были разобраны требования задания и составлен план реализации.

Помощь ИИ включала:

- проектирование доменной модели, разделение Entity и Value Object, определение
  границ агрегата и правил проверки оценок;
- выбор архитектуры Ports and Adapters, распределение ответственности между
  слоями и применение паттернов Builder, Facade и Strategy;
- помощь в реализации консольного интерфейса, расчёта итогов, JSON-хранилища,
  CSV-экспорта и DI-контейнера;
- создание и запуск тестов, проверку граничных случаев и сквозных сценариев;
- ревью соответствия требованиям, оценку необходимости файлов и абстракций;
- выявление и исправление ошибок;
- написание грамотного README файла.

Участие ИИ включало изменение кода, а не только
консультации. Проверка результата проводилась автоматическими тестами,
демонстрационным сценарием и анализом кода.
