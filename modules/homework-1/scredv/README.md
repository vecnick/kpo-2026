# ВышКат — консольная система учёта парка прокатной техники

## 1. Назначение проекта

**ВышКат** — консольное Java-приложение для учёта прокатного транспорта и сопутствующего инвентаря. Система позволяет принимать транспорт в парк после техосмотра, учитывать вещи на балансе, рассчитывать суммарное суточное энергопотребление и выводить транспорт, подходящий новичкам.

В текущей версии данные хранятся в памяти приложения. База данных, сотрудники и склад запчастей не реализованы: они не входят в обязательный объём этой версии.

## 2. Реализованные возможности

1. **Добавление транспорта:** обычного самоката (`Scooter`), велосипеда (`Bicycle`) или электросамоката (`ElectricScooter`). Перед постановкой на баланс вызывается техосмотр.
2. **Техосмотр:** `ServiceCenterImpl` отклоняет транспорт с показателем простоты менее 3; для энергопотребляющего транспорта также действует ограничение суточного расхода **150 кВт·ч** включительно.
3. **Учёт энергопотребления:** суммируется расход всех объектов, реализующих `EnergyConsumer`, включая электросамокаты и зарядные станции.
4. **Транспорт для новичков:** в список попадают принятые в парк транспортные средства с показателем простоты **от 6 до 10**.
5. **Учёт вещей:** можно добавить шлем (`Helmet`) или зарядную станцию (`ChargingStation`); общий список инвентаря содержит транспорт и вещи с их инвентарными номерами.
6. **Обработка ошибок:** проверяются непустота и уникальность инвентарного номера, диапазон простоты от 1 до 10 и корректность энергопотребления (конечное неотрицательное число). Названия моделей и вещей намеренно не валидируются: это не требуется для основных правил задания.

## 3. Устройство проекта и логика решений

| Часть проекта | Назначение |
| --- | --- |
| [`model/InventoryItem.java`](src/main/java/vyshkat/model/InventoryItem.java) | Общий интерфейс всех инвентаризируемых объектов: номер и отображаемое название |
| [`model/Transport.java`](src/main/java/vyshkat/model/Transport.java) | Контракт транспорта, включая показатель простоты для новичка |
| [`model/EnergyConsumer.java`](src/main/java/vyshkat/model/EnergyConsumer.java) | Независимый интерфейс для объектов, потребляющих энергию |
| `model/AbstractTransport.java`, `model/item/Item.java` | Базовые классы для транспорта и вещей |
| [`service/FleetService.java`](src/main/java/vyshkat/service/FleetService.java) и `service/impl/FleetServiceImpl.java` | Приёмка, хранение, проверка инвентарных номеров, отчёты |
| [`service/ServiceCenter.java`](src/main/java/vyshkat/service/ServiceCenter.java) и `service/impl/ServiceCenterImpl.java` | Контракт и реализация техосмотра |
| [`console/ConsoleApp.java`](src/main/java/vyshkat/console/ConsoleApp.java) | Ввод данных и вывод результатов в консоли |
| [`config/ApplicationConfiguration.java`](src/main/java/vyshkat/config/ApplicationConfiguration.java) | Создание объектов и связывание зависимостей средствами Spring |

Приложение запускается через `VyshKatApplication`. Spring создаёт `ServiceCenter`, передаёт его в `FleetService`, а затем передаёт `FleetService` в `ConsoleApp`. Бизнес-логика не зависит от консольного меню. Для хранения используются два списка: транспорт и вещи. Этого достаточно для учебного объёма данных; дополнительный слой репозиториев не нужен.

**Почему две иерархии и отдельный интерфейс потребления?** Транспорт и вещи обладают разными свойствами, но оба типа имеют инвентарный номер. При этом потреблять энергию могут объекты обеих иерархий. Интерфейсы `InventoryItem` и `EnergyConsumer` выражают эти общие свойства без создания искусственного общего базового класса для всего.

## 4. Применение SOLID и DI

- **SRP (единственная ответственность):** `ConsoleApp` отвечает за консольное взаимодействие, `FleetServiceImpl` — за учёт парка, `ServiceCenterImpl` — за правила техосмотра.
- **OCP (открытость/закрытость):** расчёт энергии работает с интерфейсом `EnergyConsumer`, поэтому новый потребитель можно добавить без изменения алгоритма суммирования. При этом меню `ConsoleApp` для нового вида транспорта придётся дополнить — это осознанное упрощение.
- **LSP (подстановка Лисков):** `Scooter`, `Bicycle` и `ElectricScooter` используются через интерфейс `Transport` при приёмке и формировании списка для новичков.
- **ISP (разделение интерфейсов):** не каждый предмет обязан потреблять энергию: только нужные классы реализуют `EnergyConsumer`.
- **DIP (инверсия зависимостей):** `FleetServiceImpl` зависит от интерфейса `ServiceCenter`, а `ConsoleApp` — от интерфейса `FleetService`. Конкретные реализации связываются в `ApplicationConfiguration` через конструкторы (Dependency Injection).

### Обязательные вопросы

**1. Какой принцип SOLID применён наиболее явно и где?**  
Наиболее наглядно **ISP**: [`InventoryItem`](src/main/java/vyshkat/model/InventoryItem.java), [`Transport`](src/main/java/vyshkat/model/Transport.java) и [`EnergyConsumer`](src/main/java/vyshkat/model/EnergyConsumer.java) разделяют обязанности. Например, `Helmet` не должен реализовывать метод потребления энергии, а `ChargingStation` реализует его через `EnergyConsumer`. Также хорошо выражен **DIP** в [`FleetServiceImpl`](src/main/java/vyshkat/service/impl/FleetServiceImpl.java), который обращается к `ServiceCenter`, а не к `ServiceCenterImpl`.

**2. Какой принцип сознательно ограничен и почему это приемлемо?**  
**OCP** применён не полностью в консольном интерфейсе. В [`ConsoleApp`](src/main/java/vyshkat/console/ConsoleApp.java) создание моделей организовано через `switch` по фиксированным типам. При добавлении нового транспорта потребуется новый пункт меню и ветка `switch`. Для трёх известных типов это проще и понятнее, чем фабрики, реестры и подключаемые обработчики; расширение требуется редко и локализовано в консоли.

**3. Что изменится при добавлении нового вида транспорта?**  
Например, при добавлении электровелосипеда нужно создать `ElectricBicycle`, наследующий `AbstractTransport` и реализующий `EnergyConsumer`, и добавить способ его создания в `ConsoleApp`. **Не потребуется менять** контракты `Transport`, `InventoryItem`, `EnergyConsumer`, расчёт суммарной энергии и правило отбора для новичков. Существующий `ServiceCenterImpl` также сможет проверить новый объект по общим свойствам (если для электровелосипеда не нужны особые правила). При добавлении сотрудников или склада запчастей понадобятся отдельные модели и функции, так как сейчас они не предусмотрены; текущий механизм учёта транспорта не обязан изменяться только из-за появления таких подсистем.

**4. Какой тест фиксирует техосмотр/правило для новичков и как подменяется зависимость?**  
[`ServiceCenterImplTest`](src/test/java/service/ServiceCenterImplTest.java) проверяет правила техосмотра, в том числе пограничное энергопотребление 150 кВт·ч и порог простоты 3. [`FleetServiceInteractionTest`](src/test/java/service/FleetServiceInteractionTest.java) проверяет, что `FleetServiceImpl` вызывает `inspect`, не добавляет отклонённый транспорт и отбирает для новичков технику с простотой от 6. Зависимость подменяется через **Mockito**: `mock(ServiceCenter.class)`, `when(serviceCenter.inspect(any())).thenReturn(true/false)`, после чего mock передаётся в `new FleetServiceImpl(serviceCenter)`. Вызов проверяется через `verify(...)`. Это проверка DI без поднятия Spring-контекста.

## 5. Тесты

- **`ServiceCenterImplTest`** — правила техосмотра и граничные значения.
- **`FleetServiceInteractionTest`** — взаимодействие с подменённым техосмотром, проверка дубликатов и некорректного ввода, суммирование энергии, фильтр новичков, общий инвентарь.
- **`VyshKatApplicationTest`** — проверка запуска Spring-контекста и наличия необходимых бинов (консольный бин в тесте заменён с помощью `@MockitoBean`).

Используются **JUnit 5** и **Mockito**. Утверждение о прохождении всех тестов следует делать после их фактического запуска в локальной среде.

## 6. Запуск и демонстрация

Точка входа — метод `main` класса [`VyshKatApplication`](src/main/java/vyshkat/VyshKatApplication.java). Проект можно запустить из IDE с настроенными зависимостями Spring Boot и Lombok.

**Демонстрационный сценарий:**

1. Добавить самокат с простотой **7** — успешная приёмка, устройство доступно новичкам.
2. Добавить велосипед с простотой **2** — отказ техосмотра.
3. Добавить электросамокат с простотой **6** и расходом **5 кВт·ч** — успешная приёмка.
4. Добавить зарядную станцию с расходом **3 кВт·ч** и шлем — оба предмета появятся в общем инвентаре.
5. Показать суммарное потребление — **8 кВт·ч в сутки**.
6. Показать список для новичков — самокат и электросамокат.
7. Показать общий инвентарь — две единицы транспорта и две вещи; велосипед с простотой 2 в него не попал.
8. Попробовать добавить вещь с уже занятым инвентарным номером — приложение выдаст ошибку, не добавляя дубликат.

Во всех успешных добавлениях нужно использовать **разные непустые инвентарные номера**.

## 7. Использование ИИ и самостоятельные изменения

ИИ использовался как инструмент: 
1. Анализа проекта. Для обсуждения соответствия требованиям, проверки архитектурных решений и предложений по улучшению валидации. Рекомендации не означают автоматического включения изменений в программу.
2. Генерации шаблонного кода. Пример: реализации FleetService и ServiceCenter.
3. Написания javadoc и отчета. В последний вносились корректировки автора.
4. Написания тестов. Большая часть тестов сгенерирована ИИ. Автор сам указывал что покрывать тестами.


## 8. Ограничения

Данные не сохраняются между запусками; система не ведёт учёт сотрудников, аренды и склада запчастей. Правила техосмотра фиксированы в `ServiceCenterImpl` и едины для текущих видов транспорта. Эти ограничения соответствуют небольшому учебному проекту и позволяют не усложнять решение без необходимости.
