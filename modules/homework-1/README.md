# Домашнее задание №1. «ВышКат»

Консольное приложение для учёта транспорта и вещей кикшеринга. Транспорт
попадает в активный парк только после техосмотра. Приложение считает суточное
энергопотребление, выбирает технику для новичков и выводит инвентарные номера
всех объектов на балансе.

## Запуск

Из корня репозитория:

```powershell
.\gradlew.bat :modules:homework-1:bootRun
```

Тесты:

```powershell
.\gradlew.bat :modules:homework-1:test
```

Полная проверка, включая Checkstyle:

```powershell
.\gradlew.bat :modules:homework-1:check
```

Отчёт JaCoCo создаётся в
`modules/homework-1/build/reports/jacoco/test/html/index.html`.

## Структура решения

- `model` содержит неизменяемые модели и небольшие предметные интерфейсы.
- `inspection` содержит контракт и реализацию техосмотра.
- `repository` отвечает за хранение объектов на балансе.
- `service` содержит сценарии приёмки и построения отчётов.
- `console` демонстрирует принятие и отклонение техники, регистрацию вещей и
  все требуемые отчёты.

`InventoryItem` описывает объект с наименованием и инвентарным номером.
`EnergyConsumer` выделяет только объекты с суточным энергопотреблением.
`BeginnerFriendly` содержит правило допуска новичков. `RentalTransport`
объединяет только необходимые для проката контракты. Поэтому обычный велосипед
не обязан притворяться потребителем энергии, а зарядная станция может
участвовать в энергетическом отчёте, не являясь транспортом.

Модели представлены `record` и проверяют свои инварианты при создании. Для
создания объектов в демонстрации и тестах используется Lombok Builder.

`ParkService` получает `ParkRepository` и `ServiceCenter` через конструктор.
Spring собирает приложение и подставляет `InMemoryParkRepository` и
`StandardServiceCenter`. В интеграционном тесте `ServiceCenter` заменяется
Mockito-объектом через DI-контейнер.

## Функциональные требования

1. `ParkService.acceptTransport` запускает техосмотр и сохраняет только
   принятую технику.
2. `StandardServiceCenter` принимает технику с техническим состоянием не ниже
   7 из 10.
3. `ParkReportService.totalDailyEnergyConsumption` суммирует потребление всех
   объектов, реализующих `EnergyConsumer`.
4. `ParkReportService.beginnerFriendlyTransport` выбирает принятую технику с
   показателем простоты не ниже 6.
5. `ParkService.registerEquipment` ставит вещи на баланс, а
   `ParkReportService.inventory` возвращает транспорт и вещи в порядке
   регистрации.
6. `ConsoleScenario` показывает успешный и неуспешный техосмотр, отчёт по
   количеству, энергопотреблению, технике для новичков и всему инвентарю.

## SOLID

### Single Responsibility Principle

Ответственности разделены между `StandardServiceCenter`, `ParkService`,
`ParkReportService` и `InMemoryParkRepository`. Техосмотр не строит отчёты,
хранилище не решает, принимать ли технику, а отчёты не изменяют парк.

### Open/Closed Principle

Новый вид транспорта реализует `RentalTransport` и при необходимости
`EnergyConsumer`. Сервисы работают с интерфейсами и не проверяют конкретные
классы транспорта, поэтому их изменять не требуется.

### Liskov Substitution Principle

`ElectricScooter`, `Bicycle` и `ElectricBicycle` взаимозаменяемы там, где
ожидается `RentalTransport`. Каждый тип предоставляет корректные инвентарные
данные, показатель простоты и технического состояния.

### Interface Segregation Principle

Контракты разделены на `InventoryItem`, `EnergyConsumer`, `BeginnerFriendly`,
`RentalTransport` и `Equipment`. Велосипед не реализует ненужный метод
энергопотребления, а шлем не получает методы транспорта.

### Dependency Inversion Principle

`ParkService` зависит от `ServiceCenter` и `ParkRepository`, а не от
`StandardServiceCenter` и `InMemoryParkRepository`. Это позволяет заменить
техосмотр mock/fake/stub-реализацией и подключить другое хранилище.

## Обязательные вопросы

### Какой принцип применён наиболее явно?

Наиболее явно применён DIP в `ParkService`: обе внешние зависимости передаются
через конструктор в виде интерфейсов. Подмена `ServiceCenter` показана в
`ParkServiceTest` и `ParkApplicationIntegrationTest`.

### Какой принцип сознательно ограничен?

SRP сознательно ограничен в `ParkService`: один небольшой прикладной сервис
содержит два близких сценария - приём транспорта и постановку вещи на баланс.
Разделение на два дополнительных use-case класса для текущего объёма сделало бы
решение сложнее без практической пользы. Техосмотр, хранение и отчёты при этом
уже вынесены отдельно.

### Что произойдёт при расширении?

- Новый транспорт потребует только нового класса с реализацией
  `RentalTransport`; энергетический транспорт дополнительно реализует
  `EnergyConsumer`.
- Сотрудник не является `InventoryItem`, поэтому текущий репозиторий не позволит
  поставить его на баланс. Для сотрудников нужен отдельный модуль и репозиторий.
- Простая складская вещь может реализовать `Equipment`. Если понадобятся
  количество, резервирование и движение остатков, потребуется отдельный
  складской сервис, но существующий парк изменять не нужно.

### Какие тесты фиксируют ключевые правила?

- `ParkServiceTest` подменяет `ServiceCenter` через Mockito и проверяет, что
  отклонённая техника не сохраняется.
- `ParkApplicationIntegrationTest` заменяет Spring-бин `ServiceCenter` через
  `@MockitoBean` и проверяет реальный DI-сценарий.
- `ParkReportServiceTest` и `DomainModelTest` фиксируют границу допуска новичка
  `beginnerEase >= 6`.
- `StandardServiceCenterTest` фиксирует минимальный уровень технического
  состояния.
