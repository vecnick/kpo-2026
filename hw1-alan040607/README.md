# ВышКат

Консольное приложение учёта транспорта и вещей. Python 3.12+, SOLID,
DI-контейнер `dependency-injector`, тесты `pytest`.

## Запуск

Команды выполняются из корня проекта — папки с `pyproject.toml`.

Первоначальная установка в Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

Если окружение уже подготовлено, сразу запускайте:

```powershell
.\.venv\Scripts\python.exe -m vyshkat
```

В PyCharm выберите интерпретатор `.venv/Scripts/python.exe` и запуск модуля
`vyshkat`. Рабочая директория — корень проекта, поле параметров запуска пустое.

Linux/macOS: создайте окружение командой `python3.12 -m venv .venv`, затем
в тех же командах используйте `.venv/bin/python` вместо Windows-пути.

## Возможности и демонстрация

Меню позволяет принять транспорт, добавить вещь, получить отчёт о количестве
и энергии, список транспорта для новичков и весь баланс с инвентарными номерами.
Пункт `0` завершает программу; `0` при выборе вида отменяет добавление.
Ответы об исправности: `д`/`н`. Для энергии допустима точка или запятая.
Ошибки данных выводятся в консоль без добавления объекта. EOF и Ctrl+C
завершают программу без traceback.

Программа начинает с пустого баланса. Все объекты создаются из введённых
пользователем данных; заранее заполненного парка в коде приложения нет.

Для демонстрации возможностей через меню:

1. Выведите отчёт, список новичков и баланс до добавления объектов — они пустые.
2. Через пункт `1` добавьте исправные самокат, велосипед и электровелосипед.
   Укажите разные номера и простоту 5 и 6 у двух из них, чтобы показать границу.
3. Через пункт `2` добавьте шлем, док-станцию и зарядный шкаф с заданным расходом.
4. Попробуйте принять транспорт с неисправными тормозами, затем электротранспорт
   с исправными тормозами и неисправным аккумулятором — оба будут отклонены.
5. Повторите уже занятый номер, введите простоту вне диапазона или отрицательный
   расход — программа сообщит об ошибке, сохранив баланс.
6. Проверьте отчёт, отбор новичков и инвентаризацию через пункты `3`, `4`, `5`.
   Количество и энергия должны соответствовать только принятым объектам.
7. Проверьте отмену добавления через `0` в выборе вида и завершите программу
   пунктом `0` главного меню.

Консольный адаптер только получает данные и показывает результаты. Приёмка,
правила техосмотра и расчёт отчётов находятся в отдельных сервисах.

## Правила учёта

- На баланс принимаются только транспорт и вещи; сотрудники не являются активами.
- Имена и номера непустые, пробелы по краям удаляются. Номера уникальны среди
  всех объектов и чувствительны к регистру.
- Перед приёмкой транспорта `ServiceCenter` проверяет тормоза, у электрического
  транспорта также аккумулятор. Состояние вводится пользователем.
- Отказ не меняет баланс и не занимает номер. При нескольких неисправностях
  сообщается первая причина: сначала тормоза, затем аккумулятор.
- Простота — целое число 1–10. Новичкам доступен принятый транспорт с простотой ≥ 6.
- Суточная энергия конечная и неотрицательная. Переполнение суммы отклоняет
  добавление. Отдельно выводится расход транспорта и всего баланса с вещами.
- Данные хранятся в памяти до завершения программы.

## Структура и модель

| Модуль | Назначение |
|---|---|
| [domain.py](src/vyshkat/domain.py) | Объекты, интерфейсы и проверка данных |
| [inspection.py](src/vyshkat/inspection.py) | Контракт и реализация техосмотра |
| [fleet.py](src/vyshkat/fleet.py) | Приёмка, баланс, отчёты и отбор для новичков |
| [cli.py](src/vyshkat/cli.py) | Интерактивное меню и ввод/вывод |
| [container.py](src/vyshkat/container.py) | Сборка зависимостей |
| [__main__.py](src/vyshkat/__main__.py) | Точка входа |
| [tests](tests) | Тесты модели, сервисов и консоли |

```text
Asset
├── Transport
│   ├── Bicycle
│   └── ElectricTransport
│       ├── Scooter
│       └── ElectricBicycle
└── Item
    ├── Helmet
    ├── DockStation
    └── ChargingCabinet
```

`Asset`, `Transport`, `ElectricTransport`, `Item` — абстрактные классы.
Док-станция здесь пассивная, без зарядки. Объекты неизменяемые: после приёмки
нельзя подменить номер или проверенное состояние. Баланс выдаётся кортежом-снимком.

`Inventoriable` задаёт номер и имя, `EnergyConsumer` — суточную энергию.
Это структурные интерфейсы `Protocol`: реализация предоставляет соответствующие
свойства. Поэтому шлем и механический велосипед не обязаны иметь расход энергии,
а зарядный шкаф не обязан быть транспортом. Значения проверяют конструкторы;
`runtime_checkable` позволяет отбирать потребителей энергии в отчёте.

## SOLID и принятые решения

- **SRP:** модель проверяет собственные данные, `ServiceCenter` проводит осмотр,
  `FleetService` ведёт учёт, `ConsoleApp` отвечает за взаимодействие с пользователем.
- **OCP:** новый подтип транспорта включается в учёт и отбор новичков без изменения
  `FleetService`; интерфейс `EnergyConsumer` включает его в расчёт энергии.
- **LSP:** все виды транспорта принимаются через общий контракт `Transport`.
  Обычный велосипед не требует батареи или фиктивных электрических операций.
- **ISP:** инвентаризация отделена от потребления энергии.
- **DIP:** `FleetService` получает `InspectionService` через конструктор, а
  конкретный `ServiceCenter` выбирается в контейнере.

**Наиболее явный принцип — DIP:** подмена техосмотра через контейнер реально
используется в тестах, без изменения кода учёта.

**Сознательно ограничен OCP:** новый вид добавляется в каталог `VEHICLES`/`ITEMS`
в `cli.py`, а новые поля требуют изменения формы ввода. `ServiceCenter` знает
категорию `ElectricTransport` для проверки аккумулятора. Для небольшого приложения
это проще универсального механизма плагинов и правил. Репозиторий, БД и шина
событий не нужны при единственном хранилище в памяти.

**Расширение:** новый механический транспорт наследуется от `Transport`,
электрический — от `ElectricTransport`; реализуется `kind` и добавляется пункт меню.
Учёт и отчёты сохраняются. Сотрудник — отдельная сущность вне `Asset`, поэтому
в баланс не попадает. Поштучная инвентаризируемая запчасть может наследовать `Item`;
партии и движения склада потребуют отдельного сервиса без изменения транспорта.

## DI и тестирование

`Container` использует библиотечный `DeclarativeContainer`: техосмотр создаётся
через `Factory`, парк через `Singleton`, консоль через `Factory`.
Один экземпляр контейнера обслуживает один парк; разные контейнеры независимы.

В `test_di_override_controls_admission_and_all_reports` зависимость заменяется
через `container.inspection.override(providers.Object(mock))` **до** первого
вызова `container.fleet()`. Тест проверяет принятие и отказ, вызов осмотра,
состояние баланса, энергию и список новичков. Созданный singleton сохраняет
полученную зависимость, поэтому каждому тесту предоставляется новый контейнер.

`test_service_center_decision` проверяет правила настоящего центра;
`test_beginner_boundary` фиксирует значения 1, 5, 6 и 10. Остальные тесты проверяют
дубликаты, отказ без изменения состояния, расширение модели и диалог пользователя.

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Покрытие строк и ветвлений всего пакета выводится в терминал; минимальный порог
60%. Отдельный HTML-отчёт не создаётся. Зависимости и настройки инструментов
собраны в `pyproject.toml`.

недочётов в коде, улучшения читаемости и оформления, а также написания и

техосмотра через DI-контейнер и обработка пользовательского ввода.
